27 October 2026 / Seven models / Five releases

Billing Bench

Can a coding agent build a billing system, then keep it correct as the business changes?

Each agent starts with a minimal Elixir/Phoenix scaffold and builds the same financial backend across five successive requests. It chooses the architecture, writes the code and tests, and carries its own implementation forward without feedback from the private evaluator.

Sol 6.1 approaches Astra's API correctness at a much lower cost. Astra finishes faster. Sol 6.1 passed 109–111 of 123 API cases for about $14 per run; Astra low passed 105–117 for about $54. All three Sol 6.1 runs outscored all three Sol 6 runs. No application passed every check. DeepSeek V4.1 Flash varied widely: 12–58 API cases and 2–18 of 20 retained histories across three runs. Terra's original one-turn runs passed 1/123 each; completion-assisted follow-ups reached 102–112/123. These are separate protocols from the same three starts, not six independent samples.

02 / What the results say

The difficult part is preserving the past

Terra needs explicit completion requests

All three strict runs stopped with admitted incomplete deliveries, passing 1/123 final cases and 0/20 histories. These were ordinary model turn completions, not runner timeouts or quota cutoffs. One completion request per release raised final API scores to 102, 112 and 109/123. This measures an assisted workflow, not strict one-turn reliability.

Sol 6.1 closes the API correctness gap

Sol 6.1 xhigh passed 109–111 of 123 cases, versus 71–88 for Sol 6 xhigh. Its mean of 110 is close to Astra low's 110.7, at $12.58–$15.73 per run. This comparison also changes CLI version and starting-run history; it does not isolate a model-only effect.

Retained histories remain a separate weakness: Sol 6.1 passed 16–17 of 20, versus Astra's 14–20 and Opus's 19–20.

Astra is faster; Opus remains competitive

Every Astra run finished in under four hours; Sol 6.1 took 4h 44m–6h 27m. Opus 5.5 xhigh passed 105 and 107 API cases in 3h 32m and 3h 37m, for $82.21 and $77.55. Its second run passed all 20 retained histories, versus 19 for the first. It used Claude Code; the OpenAI models used Codex CLI. Two runs offer limited evidence of variation.

DeepSeek varies sharply between runs

DeepSeek V4.1 Flash passed 50, 12 and 58 of 123 API cases, and 3, 2 and 18 of 20 retained histories. Implementation took 3h 06m–4h 50m, with 20,478–25,013 production lines. At one common Reka quote the token mixes cost $15.73–$19.01.

Run #2's low score was traced to a candidate rate-unit bug. Run #3 still omits required response fields: its four final case errors remain non-passes. Three observations show a wide spread, not a stable population variance. Harness, runtime and requested reasoning differences from other models remain uncontrolled.

Luna trades correctness for a much lower price

Luna 6 xhigh cost $2.85–$3.21 per run, but passed only 30–47 API cases and 4–7 histories. It took 6.8–8.0 hours and wrote more production code than Astra or Sol. Cheap tokens did not make the delivered applications interchangeable.

Concrete failure examples and their consequences
Mechanism Observed behavior Consequence
Unstable rounding Opus #1 passes the two customer-boundary correction checks only 4/8 and 3/8 times. Failures move both adjustments by one cent. A lucky first run can hide incorrect customer-level amounts. Both checks fail the repeated-run requirement.
Unexpected new billing Sol 6 xhigh #2 creates an extra $400 invoice in 6/8 trials after an original charge moves through two successor agreements. The customer can be billed again despite no new sale. The scenario fails even though two trials pass.
Incomplete responses Luna applications omit required fields in several API responses. These are failed interface checks. A client cannot use the promised interface. This is not necessarily a wrong monetary total or a separate bug per failed case.

Verdict: five releases are enough to distinguish these implementations. The most useful pressure comes from correcting, reallocating and reversing existing financial state. No run passed the full API suite.

04 / The workload

One application, five changing requirements

The target is a multi-tenant B2B billing backend with a deterministic HTTP contract. Infrastructure is supplied; commercial and accounting logic is not. Each release extends the same application and must keep earlier records usable.

  1. 01

    Foundation

    Catalog, subscriptions, invoices, settlement, revenue recognition, accounting rules and period close.

  2. 02

    Changes

    Effective-dated orders, retained billing policies, shared discounts, reversals and memo compensation.

  3. 03

    Metering and sharing

    Add metered usage to existing subscriptions, with pooled prices, payer policies and prepaid capacity.

  4. 04

    Agreements

    Reallocate commercial value, replace service rights, transfer billed positions and terminate successor agreements.

  5. 05

    Historical correction

    Revise old inputs after settlement, replacement and close; reconcile new debt, revenue, capacity and source ownership.

The benchmark measures autonomous implementation of a specified financial backend. It does not score UI design, product discovery or production operations. Its accounting policies define the test application, not accounting-standard compliance.

Run protocol
Codex CLI for Astra, Sol, Terra and Luna; Claude Code for Opus; OpenCode 1.18.31 with OpenRouter's Reka provider for DeepSeek. A new conversation and runtime per release; no subagents or evaluator feedback. Agents could test and revise freely. Runtime: 2 CPUs and 4 GiB RAM per candidate, with PostgreSQL and Elixir/Phoenix. DeepSeek environment
Exact model deepseek/deepseek-v4.1-flash-1017, Reka only with no fallback; high reasoning requested and a 262,144-token response cap. Quantization and native reasoning-budget equivalence are unknown. The original QEMU image was no longer available: DeepSeek uses a qualified VZ/aarch64 image with Elixir 1.20.2, OTP 29.0.4 and PostgreSQL 17.11. Scaffold, evaluator and per-candidate resources are unchanged, but runtime and harness differences are not isolated.
Terra protocols
Three independent starts, each followed through three separate branches: strict one-turn deliveries; M1-only assistance; and completion assistance at every release. The latter two are paired follow-ups, not independent samples. One generic same-session request followed each explicitly incomplete delivery, on an isolated source/database/runtime copy, with no private feedback. The latest submission always carried forward, not the best score. Fully assisted chains have five nudges each. R3 assistance in branch #3 gained 20 passes but lost one earlier passing recovery scenario; that regression is preserved. All Terra branches use the rebuilt VZ runtime; the CLI/runtime differences versus older models are not controlled away.
Correctness
123 API scenarios on each final snapshot, all scored with the same audited R4 evaluator. Four checks sensitive to randomly assigned IDs run eight times on fresh test customers and must pass every time. Every assertion in a scenario must pass. Scores describe delivered functionality, not counts of independent bugs.

20 separately evaluated histories: ten fresh/upgrade pairs ending at release 5. Upgrades retain the earlier database while switching to later submitted code. How much to trust the scores

Two scenarios have unclear requirements: whether ending an agreement with no net new charge may create offsetting billing documents, and how a correction to a closed month should be rejected or held. The headline scores keep the strict original expectations. The release table also excludes both scenarios for every run. Both Astra and Sol 6.1 remain ahead of Sol 6 either way.

A failed check can mean a wrong amount, a missing customer record, or a required workflow that does not work. The scores measure how much of the requested application works, not how many separate money mistakes it makes. The examples above explain the practical consequences.

What the time figures can and cannot tell us

These are build times, not application response times. They include model responses, tool calls and the agent's own tests. Several runs shared a host. Recorded tool-call intervals let us separate tool waiting from the rest of the run, but do not isolate slowdowns caused by other jobs or directly measure provider thinking time.

The download includes this timing breakdown for the nine older Codex runs: 89–98% of recorded time was outside tool-call intervals. We have not established a measured contention penalty. Sol 6.1's newer CLI logs contain out-of-order tool timestamps, so only its measured total implementation time is reported. Application-speed tests were not part of this rescore and are not used to rank these implementations.

What carried forward between releases?

The submitted source code and public requirements carried forward; conversations, agent home directories and running processes did not. Development databases were restored into the new runtime where a checkpoint was available. Opus #1's imported first release had no database checkpoint, so its second release began with a fresh development database. The separate retained-history tests still exercise real database upgrades for every model.

How we checked the tests

We reviewed failures against the written requirements and found mistakes in the tests as well as in the applications. After fixing the tests, we rescored all 65 release snapshots and all thirteen retained-history suites. The applications themselves were not changed.

The audited evaluator passed 73 regression tests. The audit corrected how covered billing documents and nullable accounting projections are checked, and added controls against hidden invoices, changed historical face amounts, wrong preview totals and noninteger money. Recorded traces across all five model groups were checked before live rescoring. All 78 evaluations finished without evaluator exceptions. Opus #2 adds six completed evaluations with the unchanged frozen R4 evaluator and zero exceptions. DeepSeek #1 added six verified evaluations without case errors. Its supervisor failed to parse the retained-history array after scoring; all twenty records and traces were independently verified. The readout was recovered without rerunning scoring or changing submissions. DeepSeek #2 and #3 add twelve complete jobs, bringing the total to 102 jobs and 6,562 outcomes. Run #3 has 13 raw error occurrences across releases 2–5 (four distinct final cases): missing required nested application source fields or rated-charge overage fields. Unchanged disposable replays reproduced the errors. These are candidate response-contract defects, not missing evaluations. The supervisor's stricter execution-failure labels are preserved in the receipts; all six processes exited zero with complete unique case inventories. Errors remain in the denominator and are never counted as passes. Terra adds 60 unique complete jobs across strict, assisted, intermediate and paired-before snapshots: 162 total jobs and 10,777 outcomes, with no new case errors. Shared R1 scoring receipts are counted once, not again for each branch using the snapshot. Prior evaluation jobs were not rerun.
