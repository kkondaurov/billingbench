Billing Bench

Can a coding agent build a billing system, then keep it correct as the business changes?

Each agent starts with a minimal Elixir/Phoenix scaffold and builds the same financial backend across five successive requests. It chooses the architecture, writes the code and tests, and carries its own implementation forward without feedback from the private evaluator.

Astra low delivered the strongest balance of correctness and implementation time. All three runs outscored and finished faster than all three Sol xhigh runs. Opus 5.5 landed within Astra's score range. Luna cost about $3 per run, but passed far fewer checks.

02 / What the results say

The difficult part is preserving the past

Astra is the stronger builder in this sample

Astra low passed 105–117 of 123 cases in 2.4–3.9 hours. Sol xhigh passed 71–88 in 4.8–6.2 hours. The gap is visible in every replicate, not just the best run.

Opus is competitive; one run is not a range

Opus 5.5 xhigh passed 107 API cases and 19 of 20 histories in 3.6 hours, for $77.55. That is within Astra's observed score range, at a higher cost than any Astra run. It used Claude Code; the OpenAI models used Codex CLI.

Luna trades correctness for a much lower price

Luna 6 xhigh cost $2.85–$3.21 per run, but passed only 30–47 API cases and 4–6 histories. It took 6.8–8.0 hours and wrote more production code than Astra or Sol. Cheap tokens did not make the delivered applications interchangeable.

Concrete failure examples and their consequences
Mechanism Observed behavior Consequence
Unstable rounding Opus passes the two customer-boundary correction checks only 4/8 and 3/8 times. Failures move both adjustments by one cent. A lucky first run can hide incorrect customer-level amounts. Both checks fail the repeated-run requirement.
Unexpected new billing Sol xhigh #2 creates an extra $400 invoice in 2/8 trials after an original charge moves through two successor agreements. The customer can be billed again despite no new sale. The scenario fails even though six trials pass.
Incomplete responses Luna applications omit required fields in several API responses. The repaired evaluator reports these as failed checks. A client cannot use the promised interface. This is not necessarily a wrong monetary total or a separate bug per failed case.

Verdict: five releases are enough to distinguish these implementations. The most useful pressure comes from correcting, reallocating and reversing existing financial state. No run passed the full API suite.

04 / The workload

One application, five changing requirements

The target is a multi-tenant B2B billing backend with a deterministic HTTP contract. Infrastructure is supplied; commercial and accounting logic is not. Each release extends the same application and must keep earlier records usable.

  1. 01

    Foundation

    Catalog, subscriptions, invoices, settlement, revenue recognition, accounting rules and period close.

  2. 02

    Changes

    Effective-dated orders, retained billing policies, shared discounts, reversals and memo compensation.

  3. 03

    Metering and sharing

    Add metered usage to existing subscriptions, with pooled prices, payer policies and prepaid capacity.

  4. 04

    Agreements

    Reallocate commercial value, replace service rights, transfer billed positions and terminate successor agreements.

  5. 05

    Historical correction

    Revise old inputs after settlement, replacement and close; reconcile new debt, revenue, capacity and source ownership.

The benchmark measures autonomous implementation of a specified financial backend. It does not score UI design, product discovery or production operations. Its accounting policies define the test application, not accounting-standard compliance.

05 / Method and evidence

What is included

Download results JSON
Run protocol
Codex CLI for Astra, Sol and Luna; Claude Code for Opus. A new conversation and runtime per release; no subagents or evaluator feedback. Agents could test and revise freely. Runtime: 2 CPUs and 4 GiB RAM per candidate, with PostgreSQL and Elixir/Phoenix.
Correctness
123 API scenarios on each final snapshot, all rescored with the same corrected R3 evaluator. Four checks sensitive to randomly assigned IDs run eight times on fresh test customers and must pass every time. Every assertion in a scenario must pass. Scores describe delivered functionality, not counts of independent bugs.
Retained histories
20 separately evaluated histories: ten fresh/upgrade pairs ending at release 5. Upgrades retain the earlier database while switching to later submitted code. Failures during setup remain failed histories. All ten history suites were rerun with the corrected tests.
Samples
Three runs each of Astra low, Sol 6 xhigh and Luna 6 xhigh; one Opus 5.5 xhigh. Astra, Sol and Opus reuse their own unchanged first release, then rebuild releases 2–5 with fresh conversations. Luna starts from the scaffold. This cohort does not test different effort settings within a model.
Time and cost
Time sums the five candidate implementation intervals, including tools and self-tests but excluding private evaluation and between-release or quota waits. All active retry attempts count. API-equivalent cost prices archived requests through the fifth delivery. It is a comparable usage estimate, not the subscription bill or a charge for evaluator work.
Version
Publication v1.1.0 uses the same five-release requirements and the corrected R3 tests. The earlier continuous-session results are archived separately and are not mixed into these averages.
How much to trust the scores

The main comparison survives the disputed results. Two scenarios have unclear requirements: whether ending an agreement with no net new charge may create offsetting billing documents, and how a correction to a closed month should be rejected or held. The headline scores keep the strict original expectations. The release table also excludes both scenarios for every run. Every Astra run still beats every Sol run either way.

A failed check can mean a wrong amount, a missing customer record, or a required workflow that does not work. The scores measure how much of the requested application works, not how many separate money mistakes it makes. The examples above explain the practical consequences.

What the time figures can and cannot tell us

These are build times, not application response times. They include model responses, tool calls and the agent's own tests. Several runs shared a host. Recorded tool-call intervals let us separate tool waiting from the rest of the run, but do not isolate slowdowns caused by other jobs or directly measure provider thinking time.

The download includes this timing breakdown for the nine Codex runs: 89–98% of recorded time was outside tool-call intervals. We have not established a measured contention penalty. Application-speed tests were not part of this rescore and are not used to rank these implementations.

What carried forward between releases?

The submitted source code and public requirements carried forward; conversations, agent home directories and running processes did not. Development databases were restored into the new runtime where a checkpoint was available. Opus's imported first release had no database checkpoint, so its second release began with a fresh development database. The separate retained-history tests still exercise real database upgrades for every model.

How we checked the tests

We reviewed failures against the written requirements and found mistakes in the tests as well as in the applications. After fixing the tests, we rescored all 50 release snapshots and all ten retained-history suites. The applications themselves were not changed.

The corrected evaluator passed 44 regression tests. Four deliberately corrupted Opus preview responses were rejected, while the original valid response passed. All 60 evaluations finished without evaluator exceptions. Per-case results, repeated trials, source hashes and sanitized application code are available below.
