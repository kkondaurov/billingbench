27 September 2026 / Eight runs / Five releases

Billing Bench

Can a coding agent build a billing system, then keep it correct as the business changes?

Each agent starts with a minimal Elixir/Phoenix scaffold and builds the same financial backend across five successive requests. It chooses the architecture, writes the code and tests, and carries its own implementation forward without feedback from the private evaluator.

Astra low delivered the strongest balance of correctness and implementation time. All three runs outscored all three Sol xhigh runs. Sol cost less at equivalent API prices, but took longer and produced less reliable applications.

02 / What the results say

The difficult part is preserving the past

Astra is the stronger builder in this sample

Astra low passed 103–115 of 123 cases in 3.0–3.4 hours. Sol xhigh passed 73–99 in 4.4–4.8 hours. The gap is visible in every replicate, not just the best run.

Extra effort did not guarantee a better application

Astra xhigh passed 114 cases in 4.3 hours, alongside Astra low's best result of 115. Sol low passed 76 in 4.1 hours, within the wide Sol xhigh range. These two single runs are effort probes; the three-run groups show the variation they must be judged against.

History exposes consequential mistakes

Failures include crediting the wrong amount after a revision, losing the original invoice's ownership through successive transfers, and keeping an obsolete accounting allocation after a one-cent correction. These are failures of the evolving business system, not a shortage of endpoints.

Where complete scenarios passed

Concrete failure examples and their consequences
Mechanism Observed behavior Consequence
Accounting redistribution All three Astra low runs and all three Sol xhigh runs miss the current-routing one-cent correction case. The total can be right while revenue remains in the wrong accounts. Astra xhigh passes this case.
Ownership through replacements Astra xhigh transfers 70,000 where the old billed position is 40,000, folding a new 30,000 sale into the old source. Reversing the original invoice then removes the new sale's coverage too. Several scenario failures arise from this same ownership error.
Shared customer setup Sol xhigh #3 rejects the parent-linked customer creation needed by 17 scenarios. Those workflows are unusable. Their deeper correction behavior is unobserved; this is one broad blocker, not 17 demonstrated arithmetic bugs.
Economic dates Sol low dates Jan 20 pooled usage and capacity consumption on Jan 31. Period totals can look plausible while the journal assigns service to the wrong date. Four pooled scenarios detect the same problem.
Regression during evolution Sol xhigh #3 passes half-cent rounding at release 1, then fails it from release 2 onward. Later features can break an earlier billing rule even as the cumulative number of passing cases grows.
Fixed commercial concessions Astra low #3 bills the correct 6,000 net, but exposes 8,000 in the corrected revenue-unit target. The read model and accounting workflow are inconsistent; this finding is not an overbilling claim.

Verdict: five releases are enough to distinguish these implementations. The most useful pressure comes from correcting, reallocating and reversing existing financial state. No run passed the full API suite.

04 / The workload

One application, five changing requirements

The target is a multi-tenant B2B billing backend with a deterministic HTTP contract. Infrastructure is supplied; commercial and accounting logic is not. Each release extends the same application and must keep earlier records usable.

  1. 01

    Foundation

    Catalog, subscriptions, invoices, settlement, revenue recognition, accounting rules and period close.

  2. 02

    Changes

    Effective-dated orders, retained billing policies, shared discounts, reversals and memo compensation.

  3. 03

    Metering and sharing

    Add metered usage to existing subscriptions, with pooled prices, payer policies and prepaid capacity.

  4. 04

    Agreements

    Reallocate commercial value, replace service rights, transfer billed positions and terminate successor agreements.

  5. 05

    Historical correction

    Revise old inputs after settlement, replacement and close; reconcile new debt, revenue, capacity and source ownership.

The benchmark measures autonomous implementation of a specified financial backend. It does not score UI design, product discovery or production operations. Its accounting policies define the test application, not accounting-standard compliance.

05 / Method and evidence

What is included

Download results JSON
Run protocol
Codex CLI; fresh scaffold per run; one continuing session across five staged releases; no subagents or evaluator feedback. Agents could test and revise freely. Runtime: 2 CPUs and 4 GiB RAM per candidate, with PostgreSQL and Elixir/Phoenix.
Correctness
123 deterministic API scenarios on each final snapshot, all rerun with the same audited evaluator. Every assertion in a scenario must pass. Scores describe delivered functionality, not counts of independent bugs.
Retained histories
20 separately evaluated histories: ten fresh/upgrade pairs ending at release 5. Upgrades retain the earlier database while switching to later submitted code. Failures during setup remain failed histories. These results were not rerun as part of the final API-only repair pass.
Samples
Three runs each of Astra low and Sol xhigh; one each of Astra xhigh and Sol low. Samples #1–2 use the matched five-release prefix of the preceding experiment; #3 and the effort probes are fresh five-release runs. Public requirements and scaffold bytes match. Later experimental releases and qualification runs are excluded.
Time and cost
Time sums the five candidate implementation intervals, including tools and self-tests but excluding private evaluation and between-release waits. API-equivalent cost prices archived requests through the fifth delivery. It is a comparable usage estimate, not the subscription bill or a charge for evaluator work.
Version
Version 1 covers the five releases described above. The published requirements are the ones used for these runs.
How much to trust the scores

The main comparison survives the disputed results. Seven failed checks across three runs depend on requirements that leave room for different interpretations. They remain counted as failures in the tables. Even giving all seven credit would leave every Astra low run ahead of every Sol xhigh run.

A failed check can mean a wrong amount, a missing customer record, or a required workflow that does not work. The scores measure how much of the requested application works, not how many separate money mistakes it makes. The examples above explain the practical consequences.

How fast were the applications?

All four new runs passed the basic speed checks. Astra low #3, Astra xhigh #1, Sol xhigh #3 and Sol low #1 each handled customer statements, payment recording, invoice previews and revenue-detail reads in under five seconds, with up to 128 customers. This establishes basic responsiveness at that size, not readiness for a large production workload. Speed is separate from the correctness score.

An additional test of correcting old billing data timed out on Sol xhigh #3. Other jobs were running on the same computer, so we cannot tell how much of the delay came from the application. That test is inconclusive and is not used to rank the models.

How we checked the tests

We reviewed failures against the written requirements and found mistakes in the tests as well as in the applications. After fixing the tests, we ran the same corrected suite against all eight finished applications. The applications themselves were not changed.

We also fed the tests five deliberately incorrect results and verified that they rejected each one. The test suite, individual results and source code for all eight applications are available below.
